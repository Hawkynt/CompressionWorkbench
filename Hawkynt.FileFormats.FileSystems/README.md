> Pure-managed filesystem handling for .NET, without mounting anything through the host OS. The
> package claims the WHOLE domain — every filesystem and disk-image container, modern, legacy,
> virtual-machine, optical, forensic and retro-computing alike — not a selection of it. Where a
> format is read-only, create-only or a deliberate subset, that is a tracked gap recorded in the
> [support matrix](#-support-matrix) below, which is generated from the descriptors and checked by
> the test suite.

## 📦 Installation

```bash
dotnet add package Hawkynt.FileFormats.FileSystems
```

The package bundles every `FileSystem.*` assembly and the disk-image `FileFormat.*` assemblies, with `Hawkynt.Compression.Core` as its one NuGet dependency.

## ✨ Features

- Inspect filesystems in-process without `libguestfs`, loop mounts, kernel drivers or elevated privileges — NTFS from Linux, ext4 from Windows, HFS+ from either.
- Create fresh images for every format marked WORM or R/W below, with real nested directory trees where the format has them.
- Edit existing images for every format marked R/W: add, replace, remove, purge. Some formats edit blocks in place, some lay the volume out again; the matrix says which.
- Defragment, wipe unused space, shrink and re-lay volumes at a chosen geometry on the formats whose descriptors offer it.
- Open disk-image containers (VHD, VHDX, VMDK, VDI, QCOW2, DMG, EWF, optical and tape images, firmware volumes) and reach the filesystem inside.
- Every writer is held against the format's own tools where one exists: a real kernel under QEMU, its `fsck`, or its canonical third-party utility.

## 🧩 Support matrix

| State | Meaning |
| --- | --- |
| **N/A** | Registered filesystem domain that is not represented by a standalone image/container descriptor; specialized multi-source drivers may expose mounted capabilities separately. |
| **R** | Open, list and extract only. For network, distributed and encrypted formats this may be signature/metadata detection; deliberately unverified descriptors can instead require explicit format selection and expose an opaque object. |
| **WORM** | Read plus create a fresh image; no supported edit of an existing image. |
| **R/W** | Read plus add / replace / remove / purge on an existing image. The edit may update blocks in place or lay the volume out again — the **Notes** column says when it is the latter. |

The seven verb columns are the maintenance operations the CLI and the shell gate on, read from `MaintenanceCapabilities` and defined once in [`docs/ARCHIVE-MODEL.md`](https://github.com/Hawkynt/CompressionWorkbench/blob/main/docs/ARCHIVE-MODEL.md). Each is lossless or refuses with the image untouched:

- **Defrag** lays a volume out again, and says how: *moving* relocates only the runs that are out of place through a block mover of the format's own (the `DefragmentExtents` capability, whose honoured modes `cwb maintenance <file>` lists), *rebuild* writes the volume out afresh.
- **Sort** sorts every directory by name in place, moving directory records and nothing else.
- **Wipe** zeroes what no file holds — free space, cluster-tip slack, deleted directory entries — without touching a live byte.
- **Shrink** reduces a volume to what it needs, keeping its geometry. It is absent wherever the geometry is fixed: for most read-only filesystems and for optical images there is no smaller canonical size to step to, so nothing could be reclaimed.
- **Geometry** lays a volume out again at another cluster or block geometry, keeping everything it carries. No format offers it yet: the generic relayout writes a new volume from extracted files and keeps names, bytes and modification times but not labels, serials, owners or attributes.
- **Purge** erases every live entry and leaves a valid empty image.
- **Compact** is the composite offered as one action: extent defrag, then compress, then shrink, so it is available wherever any of those is.

**Proof** is how the format is held against something outside this repository, and every tool it names links to that tool's own source, so the thing doing the checking can be reached from here. "own reader + struct-parity tests" means nothing outside this repository currently checks the format — either no such tool exists, or none is wired into the suite — so the on-disk structures are checked field by field instead. That cell is the honest gap, and it is deliberately preferred over naming a tool nobody runs: a cell that cites a checker which never executes stops anyone from going looking for one.

The `Id`, `State` and verb columns are read off the descriptors by `FilesystemReadmeIsCurrentTests`, and cross-checked against the registry's own filesystem list by `CapabilityDocumentationTests`; a row that disagrees with the code fails the build. `FilesystemVerbsAreBackedTests` then runs each ticked verb, so a cell cannot be earned by declaring an interface that refuses when called.

## 🚀 Quick start

### Walk a filesystem image

```csharp
using FileSystem.Fat;

var image = File.ReadAllBytes("disk.img");
using var fs = new FatReader(image);
foreach (var entry in fs.ListRecursive())
  Console.WriteLine($"{entry.Path} {entry.Size,10} {entry.Modified:O}");
```
### Open a virtual disk and inspect its inner filesystem

```csharp
using FileFormat.Vhd;
using FileSystem.Ntfs;

using var stream = File.OpenRead("system.vhd");
var inner = new VhdReader().OpenContents(stream);
foreach (var partition in inner.Partitions) {
  if (partition.Type != "NTFS")
    continue;
  var ntfs = new NtfsReader(partition.Open());
  foreach (var path in ntfs.WalkPaths())
    Console.WriteLine(path);
}
```

### Edit an image through the registry

```csharp
using Compression.Registry;

Compression.Lib.FormatRegistration.EnsureInitialized();
var ops = (IArchiveModifiable)FormatRegistry.GetArchiveOps("Ext")!;
using var image = File.Open("root.ext4", FileMode.Open, FileAccess.ReadWrite);
ops.Add(image, [new ArchiveInputInfo("", "etc/motd", false, "hello\n"u8.ToArray())]);
ops.Remove(image, ["var/log/old.log"]);
```

## 🧪 How the proofs run

The **Proof** column is produced by these suites, all in `Compression.Tests`. External tools that are absent make the corresponding test skip rather than fail, so the matrix records what has been shown, not what a particular runner had installed. A tool too old to read the format at all counts as absent for this purpose and skips with the version it reported — it never examined the image, so it has not judged it. A tool that does read the image and then objects has judged it, and that is a failure, never a skip.

| Suite | What it shows |
| --- | --- |
| `Support/ThirdPartyFsCheck` | Mounts the written image with the host kernel's own driver, or extracts it with 7-Zip, and compares every payload. A driver that is present and refuses the volume fails the test; only a driver that is absent lets it skip. |
| `Support/QemuRunner` (BSD guests) | A headless FreeBSD guest runs `fsck_ffs` over the written UFS volume; a DragonFly guest runs `hammer` over the HAMMER and HAMMER2 volumes. There is no Linux guest — Linux drivers are reached through the host kernel, not through QEMU. |
| `KernelMount/InPlaceRwKernelMountTests` | On a Linux host whose kernel carries the module, the host loop-mounts the package's image directly and reads the in-place-added file (MinixV1, MinixV2, NILFS2). Skips without sudo, `losetup` or the module. |
| `ExternalConformance*`, `ExternalFsInteropTests` (`Category("ExternalFsInterop")`) | `e2fsck`, `xfs_repair`, `btrfs check`, `fsck.f2fs`, `fsck.jfs`, `reiserfsck`, `fsck.minix`, `fsck.hfsplus`, hfsutils, ntfs-3g, `mkudffs`, `unsquashfs`, `mtools`, `qemu-img` accept what the package writes, and the package reads what they write. |
| DOS-era drivers under QEMU / `dmsdos` (`Cvf/MsDosRealDriverTests`, `Cvf/DriveSpace3RealDriverTests`, `CvfCreateDmsdosTests`) | MS-DOS 6.0's `DBLSPACE` and 6.22's `DRVSPACE` mount, read, write and check the DoubleSpace and DriveSpace CVFs, Windows 98's `DRVSPACE.BIN` and `SCANDISK` the DriveSpace 3 ones, MS-DOS 7.1's reads all three (opt-in media, `Support/MsDosImageStaging.md`); the `dmsdos` driver mounts every CVF, including Stacker. |
| Struct-parity unit tests | For formats with no reachable external tool, each on-disk structure the writer emits is compared field by field against the specification and read back by the package's own reader. |
Disk-image containers follow the same rule with `qemu-img`: forward `check`, raw round-trip via `convert -O raw`, and reverse — an image `qemu-img create` made is opened by the package reader. A forensic-style path builds an inner filesystem with known files, wraps it in a container, validates the container externally, then walks it back and compares bytes.

## 🧯 Filesystem-aware recovery

`FilesystemCarver` in `Compression.Analysis` scans raw images for known superblock signatures at canonical offsets, asks the matching reader to validate each candidate, and can then extract readable entries — useful when a partition table is lost but an inner superblock survives.

```csharp
using var fs = File.OpenRead("sdcard.img");
var hits = FilesystemCarver.CarveStream(fs);
foreach (var c in hits) {
  var result = FilesystemExtractor.ExtractCarved(fs, c, $"out/{c.FormatId}_0x{c.ByteOffset:X}");
  Console.WriteLine($"{c.FormatId}: {result.FilesExtracted} files, {result.FilesFailed} failed");
}
```

```text
cwb recover sdcard.img
cwb recover raw.img --mode filesystems --out out/
cwb recover raw.img --mode files --format Jpeg,Png
```

## ⚠️ Limitations

- This is an image-manipulation toolkit, not a kernel filesystem driver. R/W does not imply concurrent mount semantics, crash-consistent journaling under arbitrary interruption, or a drop-in replacement for the OS driver.
- Where **Notes** says a format's edits *rebuild* the volume, an add or remove costs the whole image rather than the bytes that changed, and the block placement of untouched files may move.
- **bcachefs** creation, in-place add/replace, reading and extraction preserve inode timestamps (to 100 ns, before the epoch and past 2038), UID/GID and permission bits when supplied through the archive-input metadata; ordinary file-backed inputs capture available host timestamps and mode automatically. Applying UID/GID on extraction depends on host APIs and is not available through the portable .NET filesystem API. Volumes are written at metadata version 1.3, the newest the distributions' bcachefs-tools open, so their `fsck` can judge them; newer tools upgrade such a volume as they open it. Mutation is profile-gated: the in-place writer owns single-device regular pointer extents as emitted by this package, and re-publishes every tree from what it read, so a volume another implementation wrote (packed keys, appended bsets, a journal with keys in it, another metadata version) is refused for mutation with the reason and left untouched; it is still read, including packed and multi-bset nodes, sparse files and symbolic links. Compressed and encrypted extents are decoded (encrypted ones with the volume key, unwrapped by the passphrase when it is wrapped); a volume opened without its passphrase lists only its carved view and refuses extraction with a request for the password. Bucket generations are carried through a mutation: emptying a bucket advances its generation, and the alloc key, the `bucket_gens` slot, the extent pointer and its backpointer are written from one source and checked against each other before the commit is published. Foreign volumes with extra live b-trees, non-canonical `bucket_gens` or `alloc_v4` keys, inline / compressed extent keys, or unsupported inode and dirent types are refused for mutation rather than rewritten speculatively (reflinked files are carried, and a removed or replaced one counts its references down — fsck and the kernel agree; defragmentation and metadata relocation refuse a volume holding them). Volumes `bcachefs format` laid out are edited in their own bucket size, 4 KiB blocks, journal placement and time base (default 128 KiB, 32 KiB and 256 KiB buckets, and b-tree nodes smaller than a bucket packed several to a bucket, proven with fsck and the kernel), and are defragmented in that layout too. Read support is broader. What a volume carries and how each value was established is written up in [BCACHEFS-ON-DISK.md](https://github.com/Hawkynt/CompressionWorkbench/blob/main/docs/BCACHEFS-ON-DISK.md).
- **ReFS** is read, and edited in one way only. The reader walks ReFS 3.x containers, MSB+ trees, allocators, Block Refcount rows and MLog framing. It lists and extracts every file of the volumes Windows Server 2022 (ReFS 3.7) and Windows Server 2025 (ReFS 3.14) formatted (4 KiB clusters, 64 KiB clusters, integrity streams), byte for byte as Windows hashes them (`RefsWindowsOracleTests`, volumes captured by `tools/foreign-os-oracles`). That includes integrity streams, whose extent entries carry a CRC32 per cluster, and the extent tables too large to embed that Windows Server 2022 moves into a separate page; a stream layout the reader does not decode is refused by name rather than extracted empty. The offline editor (replace, remove, rename, block clone, defragment) was judged by the same Windows versions: they found the replaced files corrupt or refused to mount the volume, and some refused edits had already changed the image. The one edit made is the one Windows itself makes when a file is overwritten with contents of the same length: the new bytes go over the clusters the file owns, and no metadata changes (the file keeps its old modification time). Windows Server 2022 and 2025, at 4 KiB and 64 KiB clusters, mount such a volume read-only and read-write, hash every file as written, and log no ReFS error. Length changes, resident files, sparse runs, integrity streams and shared (cloned or snapshotted) clusters are refused, as are remove, rename and defragment; the old offline editor stays internal and is tested on synthetic volumes only.
- **Reiser4** R/W reads and writes node40 and node41 (checksummed) trees of any height under every plugin profile `mkfs.reiser4 -o` can set: directory entries are keyed with the directory's own hash (r5, tea, fnv1, deg, rupasov) and fibration (lexic, dot_o, ext_1, ext_3), and the tail policy, root plugin set and backup block are carried. File bodies are extents (holes kept as holes), tails, or cryptcompress clusters compressed with lzo1, gzip1 or zstd1 at 4–64 KiB; symlinks, device nodes, FIFOs, sockets and hard links are read and written. A journal holding committed but unflushed transactions is replayed before reading, and an edit writes the replayed state. Edits, defrag, shrink and relayout are staged: the volume is read whole, edited as a plan, written to scratch, read back and verified, and only then copied over the source — refusals leave it byte-identical. New regular files are extents unless `FileBody` asks for tails, the smart policy, compressed files or the volume's own profile. Defragmentation moves extent data in place on trees of any height (twig units repointed, allocator bits moved), falling back to a rebuild when the journal is pending. A rebuild asked to reclaim space turns extent blocks that are zero within the file into holes and makes byte-identical regular files hard links of one object, then reads every file back against the source before accepting the result. A Reiser4 kernel (Linux 5.4.18 with the SFRN 4.0.2 patch, under QEMU) wrote the 13 reference volumes the reader is checked against and reads back every volume the writer makes or edits; `fsck.reiser4` calls them consistent. Long names under the Rupasov hash are keyed as the kernel keys them (reiser4progs hashes them differently, so `fsck.reiser4` flags them as it flags the kernel's own). Refused: encrypted files, short keys, block sizes `mkfs.reiser4` does not make, damaged volumes. Block sizes of 512, 1024, 2048 and 8192 bytes are read and written (`BlockSize` create option); an empty volume we make is byte-identical to `mkfs.reiser4 -b` but for the root's timestamps, superblock copies included, and `fsck.reiser4` checks every one — a Reiser4 kernel mounts only volumes whose block size equals its page size. See [native profile notes](https://github.com/Hawkynt/CompressionWorkbench/blob/main/docs/REISER4-NATIVE-PROFILE.md).
- **GFS2** R/W is the standalone `lock_nolock` profile with regular files in the root directory; small files are stuffed and larger files use the indirect tree. Existing-image edits rebuild the volume while preserving its size floor, lock-table value, UUID and each regular file's mode, owner, timestamps (with nanoseconds) and access-policy flags; layout-changing flags such as JDATA are not carried over because the rebuilt file is laid out plainly. Directory attributes are not preserved. ExHash/nested-directory writing, journal replay, cluster-lock-manager state and extended attributes remain out of scope.
- **NSS** native read support is intentionally narrow and quiescent: the reader reconstructs validated DirH/LEAF namespace relationships and ordinary contiguous file extents using the OES-derived clean-room profile in [NSS-ON-DISK.md](https://github.com/Hawkynt/CompressionWorkbench/blob/main/docs/NSS-ON-DISK.md), while retaining anchor diagnostics for unsupported images. Native allocation trees, journals, trustee metadata, ZLBH history, compressed/sparse/fragmented data profiles and writable NSS pools remain out of scope; the existing writer still emits a private Workbench container rather than a pool NetWare/OES would mount.
- **HFS+** is listed as a POSIX system shows it: a catalog '/' appears as ':' (and a ':' given to the writer is stored as '/'), file hard links carry their indirect node's data under every name, directory hard links (Time Machine snapshots) are directories holding their inode's content wherever they are linked — a link back into a directory being listed is shown but not entered, and the links add at most a million entries — and the metadata directories and journal files are left out. `.HFS+ Private Directory Data` stays visible only while it holds something no link reaches. A journal that holds transactions is replayed into what is listed and extracted, the image untouched, stopping where Apple's replay does: at the first damaged block list, dropping the transaction last opened before it. Past the recorded end the replay carries on, as macOS does, through whole transactions whose sequence numbers follow and whose block checksums hold; a torn one there is dropped. On eight journaled HFS+ and HFSX volumes macOS 26 left mid-transaction (linear, wrapped, and with a whole or a torn transaction past the end; captured by go-apfs-v3), the replay written into the image is byte-identical to what macOS's own replay leaves. hfsprogs' `fsck.hfsplus` does not replay journals; it accepts every one of those volumes once replayed and edited. Every decmpfs (HFS+ transparent compression) method is read: 1, 3/4 zlib, 5 (zeros, as libfshfs reads it), 7/8 LZVN, 9/10 raw, 11/12 LZFSE and 13/14 LZBITMAP; a dataless placeholder (0x80000001/0x80000002) has no local content and lists and extracts as empty, with `Kind` `dataless`. The writer's `Compression` option (default `None`) stores files compressed with any of those methods except 5 and the dataless types, which do not encode given content: inline in the attribute when the encoding fits (3802 bytes, files up to 64 KiB), otherwise as 64 KiB resource-fork chunks; a file that would not shrink stays uncompressed. libfshfs reads the zlib, LZVN, LZFSE and raw volumes byte for byte, 7-Zip the zlib and LZVN ones, HFSExplorer the zlib one; none of them, nor hfsfuse or Apple's open-source fsck_hfs, implements method 1 or LZBITMAP, so those two have no independent HFS+ reader here (the LZBITMAP stream itself is checked against dissect.util). The in-place editor repacks the catalog, extents overflow and attributes B-trees after each edit, growing a B-tree file into free space (one more extent at most per growth, up to eight), so an add may split nodes and a removal may empty a leaf. It adds files at any path, creating missing folders, optionally compressed (`HfsPlusModifier.AddFile` with an `HfsPlusCompression`) and with extended attributes (inline when they fit an attributes node, else in an attribute fork); data that no single free run holds is spread over several, the runs past the eighth recorded in the extents overflow file. Removing a file removes its extended attributes, decmpfs attribute, resource fork and overflow records and frees every block they own. On a case-folding volume a name differing only in case replaces the file; on a case-sensitive HFSX volume it is a second file. Removing or replacing a name of a file hard link takes it out of its indirect node: the node's link count drops, the link chain macOS keeps (previous and next link IDs in the link records' bsdInfo owner and group fields, the first link in the node's reserved1) is spliced, and the node itself — data, forks and attributes — goes with its last name; fsck.hfsplus and libfshfs accept the hdiutil volume after each of these, and fsck.hfsplus rejects it when the count is left behind. Removing a directory hard link (a Time Machine snapshot's link) splices its chain, drops its inode's link count, moves the inode's `com.apple.system.hfs.firstlink` attribute on and clears kHFSHasChildLinkMask on folders left without a directory link below them; the last link is removed only when the directory is empty — rmdir — and the inode folder goes with it; fsck.hfsplus accepts each result and HFSExplorer's unhfs extracts the same tree. Refused, the volume untouched: a hard link whose indirect node is missing or counts no names, the last link of a directory that is not empty, replacing a directory hard link with a file, editing through one, anything in the metadata directories, a fork whose extents do not add up to its block count, a special file continued in the extents overflow file, defragmentation and wiping of a volume whose journal holds transactions, and an edit of one whose journal is damaged before its recorded end. An add or remove on a volume whose journal holds transactions replays the journal into the image first and leaves it empty; a journal that is empty stays empty and valid. Defragmentation leaves the journal files where the volume header points. fsck.hfsplus accepts volumes edited each of these ways, including `mkfs.hfsplus -J`, `-s` and `-s -J` volumes and the hdiutil volume, and libfshfs reads every file and extended attribute back. On extraction, characters the host cannot hold in a file name (on Windows `: < > " | ? *`, control characters, trailing dots and blanks) become `_`, as for every format.
- Network and distributed formats generally carry no self-contained image. eCryptfs is the encrypted exception handled here: a lower file is structurally self-contained, and the passphrase profile is supported for AES-128/192/256; private-key authentication and xattr-only metadata remain unsupported.
- Disk-image container support and inner-filesystem support are separate capabilities; a container marked R/W edits the filesystem inside it through that filesystem's own descriptor.
