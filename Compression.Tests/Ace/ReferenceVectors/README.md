# ACE reference vectors

| File | Origin |
| --- | --- |
| `cafe.ace` | acefile's test corpus (droe/acefile-testdata, `codepage/ace32-cafe-filename_encoding=cp437_filenamecontains=café.ace`), written by WinAce's `ace32`: one stored member whose CP437 name contains `é`. |
| `winappdbg-head.ace` | the main header and first 35 members of acefile-testdata's `blocked_unregistered/winappdbg-winappdbg_v1.6_plain.ace` (an unregistered WinAce 2.0 solid archive of the BSD-licensed WinAppDbg 1.6 sources, 5.6 MB), cut on a member boundary. Solid members only depend on earlier ones, so the cut is itself a valid archive. ACE 2.0 blocked and stored members, directories, archive comment. |
| `ours-lz77.ace`, `ours-store.ace`, `ours-solid.ace`, `ours-encrypted.ace` | written by our `AceWriter` from the inputs in `AceTests.OursArchive` (fixed timestamps), then read by acefile. The writer must keep reproducing them byte for byte. |
| `vol-store.ace` … `.c02`, `vol-solid.*`, `vol-ace1.*`, `vol-enc.*` | multi-volume sets written by ACE 2.6 (`ACE32.EXE a -v65`, the console archiver of WinAce, unregistered) by `mkvolumes.py`: stored members split over four volumes; a solid ACE 2.0 set; a non-solid ACE 1.0 set; a solid set encrypted with `Secret`. `volumes.tsv` lists what unace 2.5 (Linux, `unace x`) extracts from each. |
| `ace26-mono8.ace`, `ace26-stereo8.ace`, `ace26-mono16.ace`, `ace26-stereo16.ace`, `ace26-rgb24.ace` | one WAVE or BMP file each (8-bit mono 11025 Hz, 8-bit stereo, 16-bit mono, 16-bit stereo; a 101 × 90 24-bit BMP; tones with a little noise and gradients, made by a small script), archived by ACE 2.6 (`ACE32.EXE a -cfg- -m5 -s- -c2 -d1024`, the console archiver from WinAce's `ace26.exe` package, unregistered). ACE 2.6 coded the WAVE files in SOUND modes 3, 4, 4 and 5 from the first byte, and the BMP as an LZ77 header followed by PIC rows (width 304, 3 planes); `AceTests` checks the modes our decoder meets. ACE 2.6 kept an 8-bit grey BMP in LZ77 and a 32-bit one in DELTA, so those were not kept. |
| `ours-media.ace` | written by our `AceWriter` (ACE 2.0, chosen by size) from the WAVE and BMP inputs in `AceMediaWriterTests.Members`, then read by acefile; the WAVE members are SOUND blocks (one followed by an LZ77 tail), the 24- and 32-bit BMPs PIC blocks after an LZ77 header (one followed by an LZ77 tail), the 8- and 16-bit BMPs DELTA. unace 2.5 tests and extracts it too. |
| `pic-kind2.ace` | a 50 × 40 24-bit BMP (`AceMediaWriterTests.Bitmap(50, 40, 24, 9, trailer: 13)`) written by a development revision of our writer that coded rows of the third plane with PIC decoder kind 2 while the reference plane held values of 128 and above. unace 2.5 extracts bytes that differ from that input (SHA-256 `1ee5f9a8…`, pinned in `AceMediaWriterTests`) and reports the CRC error; reading the reference value as a signed byte in kind 2 reproduces those bytes exactly, the unsigned reading reproduces the input. |
| `acefile-listing.txt` | acefile (master 11ed076a, pure-Python bit stream, `encoding="cp437"`) reading every archive above: name, size, compression type, quality, dictionary bits, directory flag and the SHA-256 of the extracted bytes. `ours-encrypted.ace` was read with password `secret`. |
